# AGENTS.md

Instructions for coding agents working in this repository. The design
authority is `DESIGN.md`; the how-to-run authority is the `docs/` set
(one file per topic — `README.md` only sells the app). When they disagree
with this file, they win — say so and fix the disagreement.

## What this is

A Nextcloud server app (PHP, in-process, no ExApp): a full-text-search
*platform* for the `fulltextsearch` framework that indexes into the
database the instance already runs — PostgreSQL, MySQL/MariaDB or SQLite —
with its own pure-PHP document extractors. Where things live:

- `appinfo/info.xml` — manifest; pins Nextcloud/PHP versions and declares
  the platform, the repair step and the admin settings.
- `lib/Platform/SqlPlatform.php` — the only thing the framework calls;
  thin. `lib/Backends/` — one strategy per engine. `lib/Service/` — the
  executors. `lib/Model/` + the mapping services — pure deciding.
  `lib/Extraction/` — extractors, incl. the hand-written PDF stack.
  `lib/Migration/` — schema; `lib/Migration/CreateSearchArtefact.php`
  creates the per-engine search artefacts.
- `src/` — the Vue admin card (built by Vite into `js/` and `css/`).
- `docs/` — the how-to-run authority, one file per topic: admin,
  development, testing, ci, vendoring, benchmark, releasing,
  translations.
- `tests/` — `unit` (standalone) and `integration` (needs a booted
  Nextcloud; `tests/integration-env.sh` boots one per engine).
- `benchmark/` — measured stages and kept results; `tools/` — the
  php-scoper pipeline; `.github/workflows/` — see the hard rules.

## Hard rules

- Nothing built is committed: `js/` and `css/` are build output, and
  `lib/Vendor/` is generated by the scoping pipeline. `make build` and
  `make appstore` build their own.
- Never edit `.github/workflows/phpunit-*.yml`, `lint-*.yml`, `psalm.yml`,
  `openapi.yml` and friends by hand: they are pristine nextcloud/.github
  templates plus a `<name>.yml.patch`. Change the patch (and the workflow
  it produces), never just the workflow — the weekly sync would silently
  revert it. The sync and the two weekly PR workflows (npm-audit-fix,
  update-nextcloud-ocp) open PRs through PAT secrets
  (`COMMAND_BOT_WORKFLOWS`, `COMMAND_BOT_PAT` — `docs/ci.md`); their
  scheduled runs failing while the secrets are
  absent is expected, not something to fix.

## Environment

- Work inside the flake: `nix develop` (PHP 8.2 without intl, composer,
  PHPUnit, Psalm, php-cs-fixer, sqlite with FTS5).
- The gates, in the order worth running them:
  `vendor/bin/psalm --no-cache`, `vendor/bin/php-cs-fixer fix --dry-run`,
  `vendor/bin/phpunit -c tests/phpunit.xml --testsuite unit`, then
  `npm run lint`, `npm run stylelint`, `npm run typecheck`, `npm run build`;
  after touching `composer.json` or `tools/`, also
  `composer run test:scoping` (the bundling pipeline's own proof); after
  touching `lib/Controller/`, also `composer run openapi` and commit
  `openapi.json` with `src/types/openapi/openapi.ts` (the spec and the TS
  types the CI regenerates — the card's calls are typed against them; the
  extractor sits in `vendor-bin/openapi-extractor`, one
  `composer bin openapi-extractor install` away in a tree that already
  has php-scoper).
- `vendor/` sits in a scoping steady state, not a normal one: the
  pipeline prunes every runtime package from it after each install
  (`composer/pcre` stays — Psalm loads it), so missing package
  directories are not corruption; `composer install` restores them and
  re-runs the hook that re-scopes. A new runtime dependency is just
  `composer require`: the hook scopes its whole closure, and what it
  brings must be PSR-4 or a classmap of one declared type — class names
  built from string literals ride the patcher in `scoper.inc.php`,
  whose namespace roots come from the packages' composer.json and are
  never hand-listed.
- Two tool quirks: Psalm's output carries ANSI codes (strip them before
  grepping), and `phpunit --filter` loads every suite — the integration
  ones need a booted server, so run a single class by passing its file
  path together with `--testsuite unit`.
- The four-engine integration matrix runs locally without pushing:
  `tests/integration-env.sh setup` once, then `run <engine>` or
  `run-all` (`make ci-setup`, `make ci-engine ENGINE=…`, `make ci-all`).
  Every run reinstalls a throwaway Nextcloud from this working tree.
- Benchmark-scale runs need the instance's `debug` and `profiler` flags
  OFF (`occ config:system:set debug --value=false --type=boolean`, same
  for `profiler`; restore them after): the dev defaults enable Doctrine's
  per-query backtrace collector, which exhausts the 512 MB PHP limit
  around 10k documents of indexing. Mind the disk too: the volume behind
  the dev PostgreSQL had ~4.6 GB free, a 100k stage leaves ~1 GB of table
  high-water behind after its own reset (`VACUUM FULL` reclaims it), and
  a 1M stage wants a host with ~4 GB to spare.
- The dev instance is nextcloud-docker-dev's stable34 on PostgreSQL
  (`http://stable34.local`); this repository is bind-mounted as
  `apps-extra/fts_sql`, so the instance runs the working tree live after
  a rebuild. A suite run costs the instance its files — `docs/testing.md`
  is the remedy. The demo account `user1`
  carries seven files (`museu.txt` and
  `sortida-museu.{docx,odt,pdf,ppt,xls,doc}`): a search for `museu`
  must find 7, `confirmar` only the pdf, `pagament` only the ppt,
  `pressupost` only the doc — that search is the first probe before
  blaming code. Rebuilding the files is the `tests/Fixtures.php`
  builders piped into the container (the pipe script's minimal
  autoloader maps `OCA\FtsSql\…` into `lib/` but `OCA\FtsSql\Tests\…`
  into `tests/` — mind the double-`Tests/` trap), then `occ files:scan
  --quiet user1`, `occ fulltextsearch:reset` (it asks `y`, then literally
  `reset ALL ALL`, both on stdin) and `occ fulltextsearch:index -r`.
- Browser reachability for the dev instance: the stable34 container's
  own IP (whatever `docker inspect` reports for it on this machine) is
  already a trusted domain and answers from
  the host directly; `stable34.local` needs `/etc/hosts` except under
  Playwright, whose config maps it itself — `npx playwright test` from
  the repo works as-is against the dev instance (admin login
  `admin`/`admin`; `user1`'s password resets non-interactively with
  `printf 'pass\npass\n' | occ user:resetpassword user1`). A bare
  `GET /index.php/logout` fails the CSRF check — log out through the
  user menu, which carries the token.

## Conventions

- Commit subjects read `type: sentence`, with the types the
  block-unconventional-commits gate allows (feat, fix, docs, style,
  refactor, perf, test, build, ci, chore, revert, merge, wip, and
  benchmark through the workflow patch); the body explains the why, and
  measurements beat adjectives.
- Deciding is pure, executing is impure (DESIGN.md, "Code organisation"):
  SQL and value objects are composed without touching the database; only
  the services execute.
- Every user-visible string goes through `t('fts_sql', …)` on the card or
  `IL10N` behind it; the catalogue is `translationfiles/templates/fts_sql.pot`
  (`make l10n NEXTCLOUD_DIR=…` regenerates it).
- Version bumps touch `appinfo/info.xml` and `package.json` together
  (`make check-manifest` validates the manifest against the store schema),
  and the release tarball is signed — `docs/releasing.md`.
- Migrations that have shipped are immutable; a schema change ships as a
  new `Version*` class plus, if the artefact changed, the repair step
  decides again.
- The benchmark results under `benchmark/results/` are measurements, not
  output: appending is fine, rewriting history is not.
- The admin card's ids, classes and accessible names are the Playwright
  suite's locators — that contract is why "a Vue rebuild of the same
  card passes unchanged": change them and the specs together, or not at
  all.
- A justified `@psalm-suppress` with the reason inline is accepted when
  no non-deprecated route exists (see the SQLite type mapping in
  `Application.php` and the GenericEvent listener registration); an
  unexplained one is not.
- Document formats are fixtures built in PHP (`tests/Fixtures.php`) —
  no binary blobs in the repository. The byte-level traps of each
  format (style-run counts in UTF-16 units, per-page CPs in the .doc
  paragraph table, explicit string cells so `=…` never becomes a
  formula) are documented in the builders themselves: extend those,
  don't fork them.
